Software release approval
Case type: understanding_qna.

A fictional software team is deciding whether to publish a release. This dossier contains a release policy, review comments, and an approval register. Answer by understanding authority and the stated conditions; do not estimate test coverage or compute a release score.

CONTROLLING RELEASE POLICY
A release may proceed only when functional testing is approved, operations readiness is approved, and security review is approved. The Release Owner coordinates the decision but cannot waive a required review. If any review is pending, the release action is hold. The unresolved review must be assigned to its designated reviewing team.

CURRENT RELEASE CARD
Functional testing is approved by Quality Engineering. Operations readiness is approved by Platform Operations. Security review is pending with Application Security because the audit evidence needs confirmation. The Release Owner has not approved an exception and the policy does not permit one through a chat message. The build itself completed successfully, but a successful build is not a substitute for an approved security review.

DOCUMENT PRIORITY
The signed release policy controls over draft launch plans. A draft announcement says the release is ready, but the announcement author copied an earlier release card before the security review became pending. A marketing request to keep the advertised launch date does not complete a technical review. The newest release card describes the current status.

Q&A SCOPE
Identify the release action, the team that must resolve the pending review, and whether the Release Owner may waive that review under this policy. Use action hold or proceed, the exact reviewing team name, and a boolean for the waiver question.

SUPPORTING REGISTER
Build log: The build completed and produced the expected artifacts. This establishes build success but contains no approval from the security reviewing team.
Functional approval: Quality Engineering approved the functional scenarios after reviewing the recorded results. That signoff covers functional testing and no other review category.
Operations approval: Platform Operations confirmed the deployment procedure and recovery plan. Its readiness signoff does not also authorize the security findings.
Security comment: Application Security is waiting for audit evidence to be confirmed. The comment explicitly keeps the security review pending until confirmation.
Release-owner note: The Release Owner requests that all required signoffs be completed and states that coordination authority does not include waiving a mandatory review.
Draft launch announcement: The draft uses the word ready based on an earlier card. It is publication copy awaiting review, not a release authorization.
Marketing request: Marketing asks the team to preserve the announced launch date. Scheduling pressure does not change the required signoffs in the controlling policy.
Developer chat: A developer suggests publishing while the evidence is checked. The chat has no security approval and cannot supersede the signed release procedure.
Evidence index: The audit files are present in the evidence folder but their presence has not yet been confirmed by the designated security reviewers.
Previous release card: The prior release was approved and shipped. Its signoffs apply to that previous artifact and cannot be transferred to the current release.
Support preparation: Support has drafted customer instructions and can update them after approval. Preparation of those instructions does not resolve the pending technical review.
Policy archive: The archive retains draft wording that once discussed optional reviews. The signed policy replaced that wording and requires the security review.

REVIEW NOTES
Build completion and release authorization describe different steps in this procedure. A successful artifact can exist while a required approval remains pending. The current card states both facts consistently, so there is no need to choose one as though it disproved the other.

Application Security owns the unresolved security review. The functional and operations signoffs are already approved by their designated teams. Sending the pending evidence back to one of those teams would not satisfy the policy unless Application Security supplied its own approval.

The Release Owner coordinates completion of the reviews and the eventual decision. That role is explicitly denied waiver authority by the signed policy. A desire to keep the launch schedule, even when shared by the owner, cannot create the missing permission.

The draft announcement was written from an earlier card. Its readiness language explains why nontechnical stakeholders may expect a launch, but publication copy is not a technical signoff. Correct its status after checking the current release card rather than treating the draft as approval.

The evidence folder contains the audit files, yet the reviewers still need to confirm them. Presence of files and acceptance of their contents are separate facts in the current card. The required action follows the pending status stated by the responsible review team.
